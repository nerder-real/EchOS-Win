# EchOS 右键托盘菜单卡顿 —— 分析与修复报告

**日期**：2026-09-11
**问题**：右键托盘菜单后，鼠标移动时 hover 药丸（高亮背景）迟钝、不跟手
**范围**：仅托盘菜单，非主窗口

---

## 一、根本原因（已定位并修复）

### 崩溃点：`Process.runSync` 阻塞的正是菜单所在的线程

关键证据 —— `third_party/tray_manager/windows/tray_manager_plugin.cpp:355`：

```cpp
HWND TrayManagerPlugin::GetMainWindow() {
  return ::GetAncestor(registrar->GetView()->GetNativeWindow(), GA_ROOT);
}
```

**托盘的消息窗口就是 Flutter 主窗口的同一个 HWND**，与 Dart isolate 共享**同一个 UI 线程**。

因此 `lib/main.dart` 里这个轮询会直接卡住菜单绘制：

```dart
Timer.periodic(const Duration(milliseconds: 500), (timer) async {
  final r = Process.runSync('tasklist', ['/nh', '/fo', 'CSV']);  // 同步阻塞 UI 线程
  for (final line in r.stdout.toString().split('\n')) { /* 遍历全部系统进程 */ }
});
```

**因果链**：

```
每 500ms → Process.runSync 阻塞 UI 线程 10-40ms
        → 线程消息队列停转
        → WM_MOUSEMOVE / WM_DRAWITEM 被推迟
        → hover 药丸滞后  ← 你看到的"迟钝、不跟手"
```

这解释了为什么卡顿是**周期性**的、且只在鼠标移动时明显（静止时不触发重绘就看不出）。

### 已完成的修复

**1. 移除安装器检测轮询**（`lib/main.dart`）

- 删除 `_watchForInstaller()` 函数与调用
- 删除配套的 `_closeForInstall()`（只被前者调用）
- 清理不再使用的 `kernel_manager` 导入
- `_installGoRequested()` 保留（标注 `unused_element`），供后续安装包方案复用
- 完整保留了原设计意图的注释，方便后续恢复

**2. 消除托盘状态同步的无谓 IPC**（`lib/services/tray_service.dart`）

`AppState.notifyListeners()` 有 40+ 个调用点（日志、状态、配置…），每次都走到 `_onState()`：

| 项 | 原行为 | 修复后 |
|---|---|---|
| `_rebuildMenu()` | 已有内容指纹去重 ✓ | 不变 |
| `_applyIcon()` | 无条件发 `setIcon` IPC | 仅 `proxyReady` 变化时发 |
| `_applyDockIcon()` | 无条件发 `setSkipTaskbar` IPC | 仅 `showDockIcon` 变化时发 |

新增 `_lastReady` / `_lastDockIcon` 缓存，跳过无变化的跨进程调用。

## 二、次级瓶颈（C++ 侧，尚未修改）

以下为架构层面的固有开销，**在 P0 修复后可能已不构成可感知卡顿**，
建议先验证实际效果，确有需要再动。

### 2.1 每次 hover 的重复遍历

`tray_manager_plugin.cpp:941` `CurtainRenderFor()`：

```cpp
std::vector<CurtainRow> rows;
g_self->CollectMenuView(menu, rows);   // 每次 hover 都重新遍历全部菜单项
```

`CollectMenuView` 对每个菜单项调用 `GetMenuItemInfo`，hover 跨越两行时
（旧行取消选中 + 新行选中）会触发**两次** `WM_DRAWITEM` → 两次完整收集。

### 2.2 全面板 DIB 重绘

`OverlayRender()` 每次重绘**整个面板**：

- 所有行的文字重绘（`DrawTextW`）
- panel mask 重放的逐像素线性遍历（`w × h`，已从早期的 2×w×h 次 `sqrtf()` 优化为整数表查找）
- `UpdateLayeredWindow` 提交整张位图给 DWM

而 hover 实际只改变了**两行**。

### 2.3 优化建议（如需进一步提速）

| 思路 | 说明 | 复杂度 |
|---|---|---|
| 行矩形缓存 | `g_row_rects` 已有，可复用于跳过 `CollectMenuView` 的重复遍历 | 低 |
| 脏矩形重绘 | 只重绘受影响的两行区域，而非整个面板 | 中 |
| 分离内容层与装饰层 | mask/边框是静态的，可单独缓存为一个背景层，只重绘前景行 | 高 |

**注意**：作者已在代码里做了大量优化（PanelMask 缓存、DIB 复用、字体/画刷缓存、
内容指纹去重），2.1/2.2 属于架构层的剩余空间，收益递减。

## 三、验证方法

修复 P0 后请这样确认：

1. **直接体验**：启动代理让日志高频输出，右键托盘菜单，快速划过各菜单项 ——
   hover 药丸应即时跟随鼠标。
2. **对比测试**：修改前后各录一段慢动作视频，逐帧对比药丸滞后帧数。
3. **排除法**：如果仍有轻微不跟手，说明是 C++ 侧 2.1/2.2 的固有开销，
   再按上面的优化建议处理。

## 五、关于「安装器检测」的后续说明

该机制的原始目的是：**应用运行时执行覆盖安装** 时，安装器能替换被占用的
`x-tunnel.exe` 等文件。原方案在应用侧轮询检测，代价过高。

**后续处理建议**（在安装包层面解决，不在应用内轮询）：

- 方案 A：Inno Setup 用 `CloseApplications=yes` + Restart Manager，
  但需处理「应用关闭按钮是隐藏到托盘」导致的等待卡死
  （这正是原作者当初放弃它的原因，见 `EchOS.iss:34` 注释）
- 方案 B：安装器先 `taskkill /IM x-tunnel.exe /F`（已在
  `EchOS.iss:122` 的 `CurStepChanged` 中实现），本体的 exe 文件锁则由
  Inno 自身的重试机制处理
- 方案 C：应用侧保留**极低频**检测（如 30 秒一次 + 异步 `Process.run`），
  作为过渡方案

当前已移除应用侧轮询，`EchOS.iss` 中的 `taskkill` 兜底逻辑仍然有效。
